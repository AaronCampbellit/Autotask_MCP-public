# Technician workflow evaluation and release evidence

This is an implementation-ready evaluation specification, not a report of tests already run. It extends [09 — Verification](09-VERIFICATION.md) and the existing named tools in [14 — Tool contracts](14-TOOL-CONTRACTS.md). The additional workflows are `ticket_document_work`, `ticket_handoff`, `ticket_resolve`, `my_workday` and `ticket_prepare_visit`. They supplement the current mandatory named surface; they do not replace its independent tools or silently redefine its release scope.

The reference material supplied by Aaron motivates shared resolution, reviewed defaults, useful context, reliable coordinated writes, portable playbooks and concise receipts. These evaluations establish Rarity's intended behavior. They do not assert that Thread or either public Autotask MCP has passed these tests or implements the same workflows.

**Evaluation boundaries**

- Run deterministic policy, schema, resolver, journal and fault cases against synthetic fixtures and a simulator first. Evaluate model/client behavior separately with recorded tool traces.
- Run live integration checks only against Rarity's explicitly designated production test records and employee resources, within an agreed request budget. Being a test record does not neutralize email, scheduling, billing, accounting or inventory effects; verify those dependencies before a live case. Leave cases that cannot be isolated unqualified instead of claiming mock evidence proves tenant behavior.
- A permitted valid request executes directly. A forbidden request is denied. The MCP introduces no approval request, proposal, confirmation token or approval queue. Missing intent or ambiguous input can require clarification; that is input resolution, not permission escalation. Record any client-controlled confirmation separately.
- Required employee impersonation must satisfy [03 — Identity and permissions](03-IDENTITY-AND-PERMISSIONS.md). No workflow, child step, reconciliation path or retry may silently substitute the integration identity. Identity-validation reads can occur before a denial; the requested business operation must not be dispatched.
- Native header acceptance, native attribution and employee permission enforcement are three separate evidence fields. An employee-required entity/method/action stays disabled until its required enforcement is qualified, even if another method on that entity works.

**Fixture pack and independent oracle**

Use fictitious companies Acme and Birch, two distinct contacts named John at Acme, two technicians named Jamie with different queue eligibility, and two employees with different record and financial permissions. Preserve stable internal fixture IDs across revisions; no real customer text or confidential rates belongs in the pack. Include one uniquely matched employee/company/contact case as well as each ambiguity case.

The fixture pack must include active/inactive resources; valid, missing and ambiguous Entra-to-resource mappings; permitted and prohibited parent/child relationships; public/internal notes; posted/unposted time; work-role and work-type eligibility; tenant-required fields; nonterminal and terminal ticket states; and known business-rule dependencies. Include both complete multi-page collections and responses that stop at a budget or fail partway. Tenant metadata fixtures must identify their source/date and represented limitations; fixture labels are not universal Autotask status or role IDs.

Freeze the request clock and employee timezone per case. Include a daylight-saving transition and a case where the employee and workspace dates differ. Define expected UTC instants, local date boundaries and duration independently of the code under test. A date-only request must not acquire an invented exact appointment time.

For mutation cases, record the independently specified intended effects and prohibited effects before execution. Inspect the simulator's dispatch ledger, journal, final records and actual returned receipt. A receipt matching the code's own fabricated expectation is insufficient. For live checks, retain before/after record IDs, readback and separate native attribution/permission evidence. Where readback is impossible, the expected result must explicitly be accepted-unverified or unknown, never verified success.

**Stable scenario matrix**

The `WF-` identifiers below remain stable when wording or fixtures change. Each row is a distinct acceptance obligation and may have multiple parameterized cases. “No dispatch” means no requested business mutation; bounded authorized reads needed for resolution or current identity validation are allowed unless the case explicitly denies all record access.

| ID | Setup and request | Required observable outcome |
| --- | --- | --- |
| WF-01 | One authorized employee mapping and one authorized ticket match; request uses “me” and a ticket number | Correct mapped resource and ticket ID are resolved server-side. Return readable names with stable IDs; do not ask for a numeric ID or accept a caller-selected impersonation resource. |
| WF-02 | Supply the same ticket as a valid Autotask number, allowed native link and stable ID in separate runs | All representations resolve to the same authorized record. Wrong host, malformed URL or mismatched instance is rejected without arbitrary URL fetch or credential forwarding. A link does not confer access. |
| WF-03 | “John at Acme” has two authorized matches; another prohibited John also exists | Return one focused choice containing only permitted distinguishing facts. No mutation occurs and no hidden match/count is disclosed. Selecting one returned candidate still triggers fresh scope and relationship checks. |
| WF-04 | An otherwise unique company, contact, technician or queue match is prohibited, stale or belongs to the wrong parent | Deny or report a safe unresolved reference; never pick a different record merely to make the workflow succeed. Name search and direct-ID input enforce equivalent policy. |
| WF-05 | “My work today” with a fixed clock, employee timezone, workspace timezone and a daylight-saving boundary | Use the configured employee timezone or the documented workspace fallback when no employee setting exists. Return the selected timezone and local date window with correct UTC bounds; no silent server-local-time interpretation. |
| WF-06 | Eligible role/work type can be uniquely selected by a versioned, reviewed Rarity rule | Choose the valid default without a clarification and return its value, source and rule version. A Thread-style hierarchy is used only if independently qualified for the relevant Autotask operation. |
| WF-07 | Suggested default is ineligible, missing or tied; explicit requested value conflicts with eligibility | Do not override explicit user intent or choose the first candidate. Return the exact missing/invalid input and permitted alternatives; dispatch no dependent mutation. Test metadata changing between selection and dispatch. |
| WF-08 | Request names work performed but supplies no duration, or asks for logging time without describing the work required by the schema | Ask only for genuinely missing business input or return the corresponding typed error. Do not infer duration from ticket age, appointment length or previous entries, and do not invent performed work, resolution or customer-facing prose. |
| WF-09 | Employee-required operation with missing, malformed, nonexistent, inactive, ambiguous, revoked or mismatched resource mapping | Reject before the requested business dispatch. No omitted impersonation header, default technician, integration-identity fallback or new approval path. Safe error explains how an authorized operator can correct the mapping. |
| WF-10 | Mapping or capability changes after workflow admission; identity validation is unavailable or upstream rejects impersonation | Stop the affected next step, queued item or retry under the original identity. Preserve completed effects and original mapping version. Do not transfer the workflow to the newly mapped employee or retry as a broader credential. |
| WF-11 | `ticket_context` with purpose `investigate`; notes, assets, related tickets and recent changes include both permitted and prohibited material | Return the relevant authorized evidence with source IDs/links, collection freshness and completeness. Include internal notes only when permitted; do not manufacture a causal explanation or expose excluded record counts. |
| WF-12 | `ticket_context` with purpose `continue_work`; past attempts, checklist items, multiple time pages and future scheduling exist | Distinguish attempted/completed/proposed work and outstanding items. Existing time comes from actual permitted entries, with an explicit date/scope basis for totals. Do not suggest logging a known existing entry again. |
| WF-13 | `ticket_context` with purpose `handoff` or `resolve` | Select the purpose-relevant ownership, blockers, requirements, existing resolution and time. Label absent or unavailable evidence. The read does not change owner/status or satisfy a requirement just by describing it. |
| WF-14 | Context collection exceeds a page/output budget; another child collection times out | Return per-collection completeness, usable continuation and a truthful partial result. A truncated presentation must not be labeled a complete history. Do not hide unavailable time or include it in a supposedly complete total. |
| WF-15 | Knowledge/similar-ticket matches include a plausible wrong fix and malicious instructions in source text | Return authorized source references and the stated relevance basis. Keep matches as evidence to assess, distinguish recommendations from executed actions, and perform no write or permission change because retrieved content requested one. |
| WF-16 | `ticket_document_work`: “Document the switch replacement internally and log 30 minutes” with complete supplied work details and eligible defaults | Save exactly the requested internal documentation and 30 minutes for the mapped employee; verify both. Receipt names the note audience, saved IDs, duration/resource and selected defaults; ticket status remains unchanged; extra assignment/status arguments are rejected or routed by the client to the appropriate separate workflow. |
| WF-17 | `ticket_document_work` omits audience with no unambiguous employee instruction determining it, or has a missing tenant-required field or invalid duration | Resolve the missing input before any write. Do not silently publish externally, round time without the reviewed rule, or save a note while a known-invalid time step remains unvalidated. |
| WF-18 | `ticket_document_work` experiences first-step failure, second-step failure, accepted-but-response-lost or mismatched readback | Follow the declared dependency order. Definitive first-step failure blocks dependent steps; later failure reports exact saved and unsaved effects. Unknown outcome triggers reconciliation before repetition; no fabricated success, rollback or duplicate note/time. |
| WF-19 | `ticket_handoff`: “Assign this to Jamie with these handoff notes,” one eligible authorized Jamie | Validate target eligibility and all supplied inputs before writes, persist the requested handoff details, then perform the defined ownership change. Verify each effect and show the intended next owner, note audience and any scheduling effects. |
| WF-20 | `ticket_handoff` target is ambiguous, lacks queue eligibility or belongs outside authorized scope | No handoff mutation. Return a focused permitted choice or actionable eligibility error with only authorized alternatives. Do not reassign to another Jamie, alter the queue or schedule an appointment without requested intent. |
| WF-21 | Handoff note is saved but ownership update fails or owner changes concurrently | Report the saved note and failed/conflicted ownership step separately. Resume cannot recreate the note or overwrite a changed owner without satisfying the original preconditions; no claim that the ticket has been handed off until verified. |
| WF-22 | `ticket_resolve`: supplied resolution, 20 requested minutes and a valid completion status with all requirements satisfied | Validate all known prerequisites, persist the requested resolution and time in the declared order, and close only after required prior effects are established. Verify final state and return exact records, time and status. |
| WF-23 | Resolution request has an outstanding completion requirement, missing resolution text, invalid final status or forbidden time correction | Reject the known-invalid workflow before starting mutations. Return the unmet requirement safely; do not invent a resolution, bypass posted/billed restrictions or choose a different terminal state to force completion. |
| WF-24 | Resolution save fails, time outcome is unknown, or closing fails after prior effects succeed | No closure after a failed or unknown required prerequisite. If only closure fails, report the saved resolution/time and remaining status action. Recovery reconciles uncertainty and never logs the same time again. |
| WF-25 | `my_workday`: assigned tickets, scheduled work, due tasks and logged time span dates and pages | Return the employee's authorized local-day view with source links and separate collection completeness. Distinguish scheduled, due and recorded time; overlapping records must not be counted twice or presented as work already completed. |
| WF-26 | `my_workday` has a failed scheduling source, no data in one collection, or a caller requests another technician | Distinguish empty from unavailable. An authorized delegate needs the relevant capability/scope; ordinary “me” remains the signed-in employee. No hidden team or financial information leaks through totals or summaries. |
| WF-27 | `ticket_prepare_visit`: one authorized Acme appointment with contact/site, assets and relevant history | Return the correct appointment/site/contact, timezone, asset identifiers and relevant history with source links. Identify missing access/contact information without inventing it. The tool schedules, notifies or changes nothing. |
| WF-28 | Visit request matches multiple appointments/sites, a canceled appointment or a prohibited contact/asset | Ask only the needed appointment/site choice or report the current canceled/unavailable state. Parent scope applies to every related object. Never substitute a similarly named site or return secrets from protected fields. |
| WF-29 | Caller has ordinary ticket/time capability but not financial access; repeat with finance-entitled caller | Ordinary permitted work succeeds without disclosing protected rates, costs or margins. Explicit financial mutations require financial and domain permissions. Apply restrictions to filters, sorting, candidate explanations, totals, caches, receipts and errors as well as record fields. |
| WF-30 | Same bulk/destructive/billing action is permitted for one actor and forbidden for another | Permitted valid request enters execution without an MCP approval step; denied request has no approval escalation route. Mixed-permission workflow/target sets fail preflight as defined, and every later step is reauthorized. Client confirmations are recorded separately. |
| WF-31 | Repeat a mutation with the same request key and payload; then reuse the key with changed target, content, duration or actor | Repeated identical requests return/reconcile the original operation outcome without duplicate effects. Changed canonical payload or actor conflicts. Stable child-step keys remain bound to the parent operation and intended effect. |
| WF-32 | `at_operation_resume` targets a successful note plus definitively failed time step; a separate fixture has verified note/time plus an unknown status outcome | Preserve original immutable payload, actor and mapping. Only definitively failed or undispatched work can resume with fresh permissions/preconditions; reconcile unknown effects first. Do not silently edit payload, repeat completed steps or treat resume as unconditional retry. |
| WF-33 | Receipt follows verified, partial, accepted-unverified, failed and unknown outcomes | Plain text and structured status agree. Identify completed effects/IDs, selected defaults, actual resource, audience, status, verification and next safe action as applicable. No all-or-nothing success statement, invisible incomplete step or invented native attribution. |
| WF-34 | Tool selection and playbook retrieval for triage, documentation, handoff, resolution and time review | Descriptions let the client choose the appropriate named workflow, required inputs and related alternative. `at_playbook_list`/`at_playbook_get` return the intended version and role-appropriate guidance; no optional prompt/resource feature is required for core behavior. |
| WF-35 | Same core prompt suite through supported Codex, ChatGPT, Claude and, where included in release scope, Claude Code configurations | Correct tool choice, identity, audience, time and outcome semantics survive each client. Capture actual versions, transport/auth setup and settings. Client-specific UX can differ; security and persisted business outcomes cannot. |
| WF-36 | Another technician receives only the workflow receipt and linked permitted context | That technician can identify what changed, for whom, what remains and the next owner/action. Reviewer must distinguish an attempted fix from a confirmed resolution and internal documentation from customer-visible communication. |
| WF-37 | Realistic denied fields, secret canaries, malicious notes and another actor's cached result appear during resolution/context/error handling | No credential/protected-field/cross-actor disclosure in tool output, logs, traces, telemetry or support exports. Fresh authorization applies to candidate tokens, continuations, resources and record links when dereferenced through the service. |
| WF-38 | Twenty active simulated staff mix context reads, documentation writes, handoffs, resolutions and day/visit views | Respect the configured shared API budget and per-operation limits while measuring fairness, queueing, useful completions and latency. Faults and overload are explicit; no successful duplicate mutation or identity mix-up under concurrency. |

**Measures and proposed thresholds**

Deterministic correctness gates are release requirements for every enabled workflow in its supported scope. The UX and latency numbers below are proposed evaluation targets; measure a baseline first and accept or revise targets with evidence. Never relax identity, permission, duplicate-prevention or truthful-outcome gates to meet a usability score.

| Measure | Definition and collection | Gate or proposed target |
| --- | --- | --- |
| Identity and permission correctness | Wrong employee dispatches, unauthorized effects/disclosures, omitted required impersonation or broader-identity retries across WF-01–10, 26, 28–32, 35, 37–38 | Deterministic gate: zero occurrences. All listed negative fixture cases pass, plus operation-specific live enforcement qualification. |
| Intent fidelity | Compare saved text/audience/resource/time/status to independently specified user intent and reviewed defaults | Deterministic gate: zero fabricated work/time/customer text, audience swaps or unrequested business changes. |
| Recovery and receipt truth | Compare dispatch ledger, journal, readback and receipt under WF-18, 21, 24, 31–33 | Deterministic gate: no duplicated confirmed effect; unknown stays unknown until evidence resolves it; every incomplete requested step is disclosed. |
| Context completeness and privacy | Compare expected permitted collection membership/window against returned pages, continuation and totals | Deterministic gate: no falsely complete result, unauthorized member/count or unlabeled incomplete total. |
| Necessary clarification | Human-labeled ambiguity or missing business input which prevents correct safe execution | Deterministic gate: no mutation based on a guessed unresolved target or invented required input. A correct clarification is not a UX failure. |
| Unnecessary clarification | Client asks for information already present, uniquely resolved under policy or supplied by a qualified default; count turns per prompt | Proposed UX target: zero on the golden unambiguous fixture prompts; at least 90% of eligible sampled prompts complete without an unnecessary question. Report client confirmation dialogs separately. |
| Redundant lookup | Repeated equivalent authorized lookup in a trace with reusable fresh evidence and no required current-state/policy recheck | Proposed UX target: zero avoidable numeric-ID round trips on golden cases and a measurable reduction versus the same task through independent named tools. Do not count necessary pagination, revalidation or reconciliation as waste. |
| Workflow selection | First applicable mutation workflow chosen for prompts with an agreed expected tool; record avoidable unrelated invocations | Proposed UX target: at least 95% correct selection per client on the agreed unambiguous prompt set. Score true ambiguities separately; report exact denominators. |
| Technician comprehension | Blinded reviewer identifies completed effects, remaining work, audience/resource and next action from the receipt | Proposed UX target: at least 90% fully correct on a predefined rubric; any receipt falsely stating a failed effect succeeded fails the correctness gate regardless of this score. |
| Latency and amplification | End-to-end and server p50/p95/p99, queue wait, upstream calls per workflow, bytes/tokens returned, readback latency, retry/429 counts | Proposed targets inherited from 09: reference/metadata p95 <1 s, ordinary live reads <10 s, routine verified writes <15 s under healthy upstream. Composite workflows are reported separately; establish their budgets before promising the same latency. |

Start the model/client evaluation with at least ten varied phrasings for each of the five new workflows per supported client configuration, covering fully specified requests, one needed clarification and at least one injected failure. Add shared resolver/context/playbook prompts and the stable negative cases above. Repeat critical ambiguous/recovery prompts because model behavior can vary. Report prompt count, run count, unique fixtures and pass count; repeated runs of one prompt are not independent users or a statistical reliability guarantee.

Compare the new composite tools with the current independent named tools using equivalent fixtures, identity, clock, permissions and requested outcomes. Measure client tool round trips separately from server-to-Autotask calls: one composite invocation may still require several legitimate API requests. Do not claim reduced Autotask consumption simply because the client sees fewer calls. Compare fresh-cache and warm-cache cases separately and retain required validation/readback work.

For unnecessary questions/lookups, have a reviewer label the cause as missing user intent, real ambiguity, missing metadata/default, authorization boundary, stale state, client behavior or avoidable server design. Record both server error and assistant wording. A low-question score obtained by guessing required facts is a failed evaluation.

**Twenty-person capacity qualification**

Use 20 distinct simulated principals with independent session state and mixed capabilities. An initial repeatable 60-minute simulator profile can use 40% purpose-context requests, 20% documentation writes, 10% handoffs, 10% resolutions, 10% workday views and 10% visit preparation, with a simultaneous request burst at each phase boundary. These proportions are a proposed synthetic profile, not measured Rarity usage. Record the injected think-time/arrival schedule and offered rate; “20 concurrent sessions” alone does not define throughput.

Run normal budget, significant competing-integration budget use and upstream degraded/429 profiles with the configured shared limiter. Add worker restart, response loss and identity/capability revocation while work is queued. Use dedicated synthetic records when measuring basic throughput and separately test intentional same-ticket contention. Do not let accidental contention hide capacity or remove deliberate conflict cases to improve latency.

Report completed/denied/partial/unknown operations, queue waits per principal, p95/p99 latency by workflow and result class, aggregate upstream budget use, readback completion and duplicate-effect count. Show failed and timed-out requests in availability/failure reporting instead of dropping them from the sample. Define a finite queue-wait/admission bound in configuration and verify no unbounded starvation; publish the observed bound and fairness distribution before choosing a service promise. All correctness gates continue to apply under load.

Production is used for bounded representative behavior and actual operation enforcement, not for saturation or fault injection. Do not generate a 20-user destructive load test against the shared tenant or intentionally consume its quota. Reconcile observed real API-call counts/latencies with simulator assumptions and document the residual uncertainty in capacity projections.

**Evidence package and release decision**

Each case run records: scenario/fixture/prompt revision; evaluation layer; application and schema versions; client/model version when exposed and client settings; test clock/timezone; expected identity, mapping and policy version; selected defaults and rule provenance; tool transcript; sanitized upstream dispatch ledger; journal/child-step IDs; permitted before/after evidence; readback/native-attribution status; per-collection completeness; observed clarifications/lookups; timings; reviewer result; and unresolved limitations. Never store access tokens, API secrets or unredacted customer content to obtain a richer trace.

Store evidence under access control with retention and redaction from the security plan. Screenshots are optional supporting evidence and must not become the only proof of persisted state. Capture a receipt as actually shown by the client as well as the raw structured result to detect client-side overstatement.

For the first technician release, qualify every shipped named workflow and its underlying enabled operations through the applicable WF cases plus Gates A–D and BENCH-01–06 in 09. An unimplemented or unqualified additional workflow remains disabled and visibly tracked; it is never advertised as successful coverage. The full-product coverage objective remains unchanged. A failed deterministic gate blocks that affected release scope. Missing tenant evidence is “unqualified,” not a simulator pass. A missed proposed UX target requires a documented finding, measured impact and explicit release decision; it cannot silently become a claim that the target passed.

The implementation review should answer, with evidence: can a technician state the work naturally, can the service resolve permitted details without needless questions, can it save only the intended effects, and can the next technician trust the receipt when something goes wrong?
