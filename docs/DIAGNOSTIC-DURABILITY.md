# Diagnostic durability and recovery

The diagnostic store is separate from business journals. Migration `019_diagnostics` creates immutable encrypted events, searchable call projections, linked provider rows and instance heartbeats. A dedicated `DiagnosticCipher` key ring uses its own authenticated encryption domain. Retain the previous decryption keys through their seven-day event window when rotating keys; do not substitute workflow intent envelopes.

Every execution start awaits PostgreSQL persistence or a persistent encrypted spool append. The spool uses one immutable framed segment per event, with a checksum, exclusive file creation, file fsync, atomic publication and directory fsync. Segments are owned by a process UUID. Recovery skips recently heartbeating owners; stale incomplete frames are quarantined visibly, while complete frames are recovered. A corrupt committed segment is retained as a quarantined frame and blocks healthy admission rather than silently disappearing.

Spool placement must be on a persistent volume. The deployment filesystem's fsync and rename behavior must be verified separately. Start admission requires free space exceeding a terminal-event reserve based on the configured concurrency and maximum encrypted frame size. Nonterminal fallback events cannot consume that reserve. Terminal events may use it. The configured concurrency must cover all admitted MCP and background execution sources. No event-count quota, sampling or unexpired-event eviction is present.

Delivery is at least once. UUID constraints deduplicate replay; terminal precedence prevents stale interrupted records from overwriting completed results. Spool deletion follows committed delivery or original-timestamp expiry. Recovery never invokes a business operation. If both durable sinks fail, new execution stops. Failed terminal evidence remains pending for durable recovery; the already returned native acceptance/result is not converted into a retryable business failure. Recovery records the storage interruption before reopening admission.

Call projections expire seven days after their start. Events expire seven days after their own occurrence. Every query filters expiry immediately. A one-minute maintenance worker independently removes expired spool/quarantine records, drains committed events, refreshes its instance lease and processes up to twenty bounded database cleanup batches. Expired starts belonging to a different instance whose heartbeat has stopped for two minutes become interrupted with unknown outcome, never inferred safe to retry. The deployment remains a single-server topology; the two-minute lease should exceed expected healthy maintenance delays.

Administrators must be current platform administrators in the same tenant. Lists return bounded metadata pages and encrypted filter/actor-bound cursors. Spool-backed queries stream pending files, merge terminal evidence and explicitly report degraded/incomplete history while delivery is pending or PostgreSQL is unavailable. Detail/export retains the normal current-access check and separate administration audit. The spool provides operational visibility during a database outage; it is not a replacement indexed history database.

Use bounded diagnostic database connection/query/statement timeouts so a stalled database can fall back to the spool. Health reports capture failures, pending failed events, spool bytes/events/oldest timestamp, available space, reserved space, torn frames and cleanup sweep time. Quarantined unexpired frames require operator review; do not delete them merely to make readiness green. Expand storage when capacity becomes insufficient.

Tests cover PostgreSQL atomic materialization, deduplicated replay, encrypted details, total storage failure, preserved accepted-write outcomes, live-owner recovery exclusion, torn frames, seven-day expiry during database outage, interrupted-call recovery, terminal precedence, tenant/admin/cursor boundaries and capture above 1,100 calls without a daily cutoff. Real HTTP tests cover successful calls, unknown tools, pre-SDK attachment validation, wrapper parentage and fail-closed admission.

These are source and fixture results. Deployment-volume durability, sustained p95/p99 overhead, production capacity and backup/WAL/snapshot retention remain deployment acceptance checks. Active-store expiry does not claim deletion from backups; diagnostic data must not silently inherit an incompatible backup retention policy.

## Configuration and rotation

Set `DIAGNOSTICS_ENABLED=true`, an absolute `DIAGNOSTICS_SPOOL_DIRECTORY` on the dedicated persistent `diagnostic-data` volume, and a distinct base64 32-byte `DIAGNOSTICS_ENCRYPTION_KEY`. For rotation, replace the single-key setting with secret `DIAGNOSTICS_KEYRING` JSON containing `active` and `keys` (key ID to base64 key), up to eight keys. Preserve old IDs/keys until their events and pending spool frames expire; the initial single key has ID `1`. The two key settings are mutually exclusive. Never commit populated key configuration. The live factory uses a separate four-connection diagnostic pool with two-second connection/query/statement limits.

Diagnostics is disabled by default until provisioned. The server image includes a mode0700 spool directory owned by the unprivileged application user; Compose mounts it outside the writable layer. This establishes packaging, not deployment-filesystem or backup acceptance.
