# Autotask time approval API boundaries

Autotask uses several different approval flows that should not share one ambiguous MCP mutation:

| Business action | Captured REST API support | Current MCP |
| --- | --- | --- |
| Approve a timesheet or Approve & Post time | No timesheet approval or posting route appears in the captured 231-entity REST index or tenant Swagger. `TimeEntries` exposes create/update/query/delete, but its documentation says API-created ticket/task time must still be approved and posted. | No approval/post action. The MCP must not claim a billing-approval row posts or approves a timesheet. |
| Record a billing approval level for one time entry | `BillingItemApprovalLevels` supports query/get/create. Its required fields are `timeEntryID`, `approvalLevel`, `approvalResourceID`, and `approvalDateTime`. The parent `TimeEntries` record exposes `billingApprovalLevelMostRecent`, `billingApprovalDateTime`, and `billingApprovalResourceID`. | `time_billing_approval_review` and `time_billing_approval_record` are implemented locally with an exact prior-level check, a one-shot create, and row/parent readback. This records a billing level only; the parent approval date/resource workaround is intentionally not automatic. Native write and client discovery remain unverified. |
| Approve or reject a time-off request | `TimeOffRequestsApprove` and `TimeOffRequestsReject` are separate child actions; `ResourceTimeOffApprovers` identifies approvers. The captured Swagger exposes `GET TimeOffRequests/{id}/Approve` and `POST TimeOffRequests/{id}/Reject` with `TimeOffRequestRejectModel` body, so even the HTTP verbs differ. Autotask requires API-user permission to approve time off via impersonation and an impersonated resource who is a configured timesheet approver. | `time_off_approver_resources`, `time_off_review`, `time_off_approve`, and `time_off_reject` are implemented locally. They require the mapped actor to be the next configured approver, verify expected status/level before dispatch, send the actor header only on these documented approval actions, and read back. Native impersonation and write permissions remain unverified. |

The [Autotask BillingItemApprovalLevels reference](https://autotask.net/help/developerhelp/content/apis/rest/entities/BillingItemApprovalLevelsEntity.htm) says creating a level updates `TimeEntries.billingApprovalLevelMostRecent` but does not reliably set the approval date/resource fields. It documents a second TimeEntries update as a workaround. That creates a partial-success boundary: a robust workflow would journal the two effects separately, never repeat the first create after uncertainty, and verify both records.

The [Autotask TimeEntries reference](https://webservices.autotask.net/help/developerhelp/Content/APIs/REST/Entities/TimeEntriesEntity.htm) states that submitted or approved timesheets restrict edits and that REST-created ticket/task entries still require approval and posting. The [Autotask time-off approval reference](https://ww19.autotask.net/help/developerhelp/content/apis/rest/Entities/TimeOffRequestsApproveEntity.htm) documents its separate impersonation permission and approver requirement.

The local implementation also adds `time_timesheet_review`: a bounded employee time-entry view with page-scoped hours and billing fields. It explicitly reports native timesheet approval/posting status as unavailable via REST. Leadership tools require the separately granted `time.approve` capability and corresponding area permissions. The work-management pack must be enabled, and approval mutations additionally require its writes switch. No permission is granted to existing team-time readers automatically.

The native route and request model were rechecked against the public zone Swagger at `https://webservices5.autotask.net/atservicesrest/swagger/docs/v1` on September 23, 2026. This confirms `GET /V1.0/TimeOffRequests/{parentId}/Approve`, `POST /V1.0/TimeOffRequests/{parentId}/Reject` with `TimeOffRequestRejectModel.reason`, and `POST /V1.0/BillingItemApprovalLevels`. Live tenant authorization and results still require qualification.
